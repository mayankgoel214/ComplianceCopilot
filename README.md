# Verity

[![CI](https://github.com/mayankgoel214/Verity/actions/workflows/ci.yml/badge.svg)](https://github.com/mayankgoel214/Verity/actions/workflows/ci.yml)

Reads a research or academic document, works out which regulatory frameworks it
touches, retrieves the sections that actually apply, and reports what is missing
— quoting the regulation behind every finding, and **checking that the quote is
real before you see it**.

Live, no account needed: **https://verity-compliance.vercel.app**

- `/assess` — paste a document, or run the sample, and get findings with verified citations
- `/search` — one query ranked three ways at once, so you can disagree with the evaluation
- `/evaluation` — recall@k, MRR and nDCG on a held-out labelled set, including the configurations that lost

An 84-second walkthrough recorded against the live site is at
[`docs/verity-demo.mp4`](docs/verity-demo.mp4). It is produced by
`npx tsx scripts/record-demo.mts` followed by `python3 scripts/caption-frames.py`,
so its numbers are whatever the deployment returned while it ran.

---

## The problem this is built around

An LLM asked about compliance will produce findings. It will also produce
citations, and the citations will look exactly like the real ones. A tool that
prints both in the same typeface has not helped anybody.

So every finding here carries two quotes — one from your document, one from the
regulation — and both are checked against their sources before the response is
returned. A finding whose regulation quote cannot be found in the passages the
model was actually shown is marked **unsupported**, excluded from the score, and
still displayed. Hiding it would make the tool indistinguishable from one that
never checked.

## Retrieval, measured

`docs/retrieval-eval.md` is generated by `npm run eval`. It compares six
configurations — BM25, dense retrieval, int8-quantized dense, equal-weight rank
fusion, weighted fusion, and fusion followed by an LLM listwise reranker — on a
gold set of labelled queries, split into

- **dev** — queries phrased close to the regulation's own language,
- **test** — queries written the way a practitioner describes a situation, deliberately avoiding the target section's vocabulary,
- **lookup** — bare citation lookups such as `45 CFR 164.312`.

The one fitted parameter in the whole stack — the fusion weight — is chosen on
dev alone. BM25's k1 and b are the standard defaults, RRF's k is the value from
the paper, and the chunk size is left where it started for reasons the chunking
experiment below sets out.

On the 32 held-out paraphrased queries:

| Configuration | Recall@10 | MRR@10 | nDCG@10 | Median |
| --- | --- | --- | --- | --- |
| BM25 | 28.1% | 0.172 | 0.178 | 0 ms |
| Dense, 768d | 84.4% | 0.651 | 0.666 | 1 ms |
| Dense, int8 | 84.4% | 0.657 | 0.665 | 1 ms |
| Equal-weight RRF | 55.7% | 0.377 | 0.383 | 1 ms |
| Weighted RRF | 84.4% | 0.651 | 0.666 | 1 ms |
| **Fusion + rerank** | **90.6%** | **0.741** | **0.776** | 11.5 s |

Two findings, and the negative one is the more useful. **Fusing BM25 into dense
retrieval makes things worse here**: the weight sweep picks a lexical weight of
zero, and equal-weight RRF — the textbook default — drops nDCG@10 from 0.666 to
0.383, because BM25 is much the weaker arm and an equal vote is the wrong prior.
The lookup slice is in the report so the query class where the lexical arm *is*
indispensable is on the page too; there, equal-weight fusion wins outright.

**Reranking is where the quality is.** It costs 11.5 seconds against one
millisecond, which is stated as a tradeoff rather than buried.

## How a run works

```
classify → decompose into probes → retrieve → assess → verify → score
```

1. **Classify** — one call decides which of eight frameworks the document
   touches, and must say what in the document triggered each one.
2. **Decompose** — the same call emits short *concerns*: the specific things in
   this document that might create an obligation. Those become the retrieval
   queries. Embedding a whole document as one vector retrieves nothing in
   particular.
3. **Retrieve** — each concern is embedded and matched against the corpus,
   filtered to the framework in question.
4. **Assess** — the model sees the document and the retrieved passages, and must
   quote both for every finding.
5. **Verify** — both quotes are checked. Exact, near, or unsupported.
6. **Score** — arithmetic over the *supported* findings, not a number asked of
   the model. A reader who disagrees with the score can point at the finding
   that caused it.

Frameworks are assessed concurrently. A sample run is about 25 seconds and
roughly $0.008 in generation at published rates; the response carries a
per-stage trace with timings and token counts, and the page will show it to you.

## The corpus

413 sections, 1,147 passages, assembled by `npm run corpus:fetch` from
authoritative public sources:

| Framework | Source |
| --- | --- |
| FERPA | 34 CFR Part 99 |
| IRB / Common Rule | 45 CFR Part 46 |
| HIPAA | 45 CFR Parts 160 and 164 |
| ADA / Section 508 | 36 CFR Part 1194, including appendices |
| Export controls | 15 CFR Part 734 (EAR), 22 CFR Part 120 (ITAR) |
| GDPR | Regulation (EU) 2016/679 |

US federal regulations are works of the United States government and are not
subject to copyright; the GDPR is published by the EU.

**SOC 2 and ISO/IEC 27001 are deliberately absent.** Their text is copyrighted
by the AICPA and ISO and cannot be redistributed here. Verity still classifies
documents against them, and then says outright that it has nothing to cite —
rather than paraphrasing a standard it is not allowed to republish.

## Running it

```bash
npm install
cp .env.example .env.local        # then add GOOGLE_GEMINI_API_KEY
npm run dev
```

The index in `data/` is committed, so a clean clone serves `/search` and
`/evaluation` immediately. A Gemini key is needed for anything that embeds a
query or calls the model.

```bash
npm run typecheck                 # tsc --noEmit
npm test                          # unit + integration (pgvector suite skips without a database)
npm run test:e2e                  # Playwright, against a running dev server
npm run test:db                   # starts Postgres+pgvector in Docker, runs the store suite against it
npm run corpus:fetch              # rebuild corpus/ from the source regulations
npm run index:build               # re-chunk and re-embed into data/
npm run eval                      # regenerate docs/retrieval-eval.md and eval/results.json
```

`npm run index:build` takes `--target-tokens` and `--overlap-tokens`, so a
chunking experiment is a rerun rather than an edit. Embeddings are cached by
content hash, so only the chunks whose text actually moved are re-embedded.
`npm run eval:chunking` does the whole sweep and writes
[`docs/chunking-experiment.md`](docs/chunking-experiment.md).

That experiment's result is a null one, which is why it is worth reading: across
a fourfold range of chunk sizes, dense nDCG@10 moves between 0.662 and 0.685 — a
spread smaller than a 32-query slice can resolve. Larger chunks put the answer at
rank 1 more often, smaller ones cover more by rank 10, and the shipped
configuration is deliberately left alone rather than tuned to a held-out number.
Chunk size is a knob that gets turned by reflex in RAG systems; on this corpus it
is not where the quality is. Reranking is.

## Design notes

**No vector database.** The corpus is around a thousand passages. An exhaustive
scan of a flat `Float32Array` answers in single-digit milliseconds, so an
approximate index would buy a recall loss and a dependency to solve a problem
this corpus does not have. `src/lib/retrieval/pgvector-store.ts` is the backend
for a corpus that outgrows this one — and it is exercised against a real
Postgres in Docker, not a mock, because this project once shipped a ChromaDB
client pointed at a `localhost` that production never had.

**768 dimensions, on purpose.** `gemini-embedding-001` is natively 3072 and
accepts `outputDimensionality`. The LangChain wrapper accepts that option and
does not send it, so every vector came back at 3072, failed the dimension check,
and fell through to a fallback. The embedding calls go straight to the REST API
for that reason.

**No silent fallbacks, anywhere.** There was once a path here that substituted
synthetic vectors when an embedding request failed, so retrieval returned
confident nonsense while every log line said success. A failed embedding is now
a failed embedding, a classifier that finds nothing returns nothing, and a
truncated model response says it was truncated instead of surfacing as a JSON
parse error twelve frames away.

**Constrained decoding, then validation.** Prompt schemas are zod, converted to
Gemini's `responseSchema` subset by `src/lib/ai/zod-to-gemini.ts`. The schema
stops the model inventing key names; the zod parse still runs afterwards,
because the OpenAPI subset cannot express a confidence in `[0, 1]`. One repair
attempt on failure, then a hard error.

## Stack

Next.js 15 (App Router, RSC) · TypeScript strict · Tailwind · Gemini
(`gemini-3.6-flash`, `gemini-embedding-001`) · zod · Jest · Playwright ·
Postgres + pgvector via Docker · Vercel.

Retrieval — BM25, cosine over a flat vector matrix, int8 quantization,
reciprocal rank fusion, and an LLM listwise reranker — is implemented in this
repository rather than imported.

## What this is not

Not legal advice. It reads documents and cites regulation text; it does not tell
you whether you are compliant. It is a portfolio project, and the evaluation is
candid about how small the labelled set is and who wrote the labels.
