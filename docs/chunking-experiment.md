## What each configuration is

- **160 / 32** — Small chunks. More of them, each more focused. 2117 chunks.
- **320 / 64** — The shipped configuration. 1147 chunks.
- **320 / 0** — The shipped size with no overlap, to see whether the overlap earns its cost. 1079 chunks.
- **640 / 128** — Large chunks. Fewer of them, each carrying more context and more noise. 692 chunks.

## Reading it

The held-out slice is 32 queries. One query moves recall by about 3.1 points, so differences below that are noise and the table should be read for its shape, not its decimals.

Relevance is judged at section granularity, which interacts with chunk size in a way worth naming: smaller chunks put more passages from the same section into the top ten, and the harness deduplicates by section before scoring, so a small-chunk configuration is not rewarded for filling the results with one section. That is the right behaviour, and it is also why smaller chunks do not automatically win here.

## Conclusion

**Chunk size barely matters on this corpus, and the shipped configuration is not being changed.**

Across a fourfold range of chunk sizes, dense nDCG@10 moves between 0.662 and 0.685 — a spread smaller than the resolution a 32-query slice supports. What does show a consistent shape is a tradeoff rather than a winner: larger chunks carry more context and are likelier to put the answer at rank 1 (37.0% to 43.2% R@1), while smaller chunks cover more ground by rank 10 (81.3% to 84.4% R@10). Overlap behaves the same way in miniature — dropping it lifts MRR and costs recall at depth.

The nominally best row here is 320 / 0. It is not being adopted, for two reasons. Its margin over the shipped configuration is 0.019 nDCG on 32 queries, which is inside the noise this set can resolve. And these are *held-out* numbers: choosing a configuration because it scored well here would fit the stack to the test set, which is the one thing the split exists to prevent. A parameter that cannot be chosen on the development slice is a parameter that should be left where it is.

The useful finding is the null one. Chunk size is a knob that gets tuned by reflex in RAG systems; on this corpus, within this range, it is not where the quality is. Reranking moved nDCG@10 by 0.110 on the same slice. That is where the quality is.
